# IPT2 Activity: Student Manager

Build a simple React + Express + Node.js CRUD application. This starter follows the Student Manager activity in `IPT2_Mentoring_Final.pptx`, especially the MVC, React state, API integration, and final-project sections.

**Activity adaptation:** MongoDB and Mongoose are intentionally omitted. The server keeps records directly in the `studentStore` variable. No database installation, connection string, account, or `.env` file is needed.

## What is already prepared?

- Express server on `http://localhost:8000` with JSON parsing and CORS for `http://localhost:3000`.
- React + Vite client on `http://localhost:3000`.
- Student routes connected to named controller functions.
- Two fictional seed students and the next available numeric ID.
- React state, forms, table, loading display, and feedback areas.
- **11 empty activity functions** with task comments above their declarations. Their bodies contain no solution code.

The starter launches, but CRUD is deliberately unfinished. Until students implement the handlers, form fields do not retain typed values, buttons do not perform CRUD, and the table is empty. A request to an empty backend controller stays pending because it does not send a response. Use `/hello` to check server setup first; cancel unfinished requests in Postman.

## Learning objectives

1. Follow a request from a React form through a route to an Express controller.
2. Read and modify an array of student objects in server memory.
3. Use GET, POST, PUT, and DELETE with JSON responses and suitable status codes.
4. Refresh React state after successful changes and show useful feedback on failures.

## Setup

Use Node.js 22.12 or newer and npm. From this project folder:

```sh
npm install
```

Start the backend in terminal 1:

```sh
npm run server
```

Start the frontend in terminal 2, also from the project folder:

```sh
npm run client
```

Open `http://localhost:3000`. Visit `http://localhost:8000/hello` separately. It should return:

```json
{ "message": "Hello IPT2!" }
```

Keep both terminals running. If port 3000 or 8000 is already in use, stop that other application first. Use `localhost` consistently because the CORS origin is configured for it.

The model is a plain JavaScript object, not a database model. Work directly with `studentStore.students` and `studentStore.nextId` in the controllers. The intended data flow is:

```text

React table <- React state <- JSON response <- controller
```

## Student record and validation rules

Each record has these properties:

| Field | Type | Rule |
| --- | --- | --- |
| `id` | Number | Generated by the server, unique positive integer |
| `name` | String | Required, trim whitespace, must not be empty |
| `gender` | String | Required, trim whitespace, must not be empty; free text |
| `section` | String | Required, trim whitespace, must not be empty |
| `hobby` | String | Required, trim whitespace, must not be empty |

Check types before trimming. Reject missing fields, null bodies, arrays, non-string fields, and whitespace-only values with status 400. Copy only the four allowed fields into a record so a submitted `id` or extra property cannot overwrite server-managed data. Browser `required` inputs help users, but the backend must also validate requests.

For `:id`, accept only a positive integer. Route parameters and number-input values arrive as strings. Convert and validate the ID before comparing it with numeric record IDs. Reject malformed IDs with 400, and return 404 for a valid ID that is absent. Do not mutate data on any failed request.

## Part A: Backend functions

Complete `server/controllers/studentController.js` in order. Keep the existing exports and routes.

| Task | Function | Required behavior |
| --- | --- | --- |
| 1 | `getStudents(req, res)` | Respond with the entire `studentStore.students` array and status 200. An empty store returns `[]`. |
| 2 | `createStudent(req, res)` | Validate all four fields. Generate the ID from `nextId`, increase the counter, append the record, and respond with the created object and status 201. |
| 3 | `updateStudent(req, res)` | Validate the ID and all four fields. Find the existing student, replace all four editable fields while retaining its ID, and respond with the updated object and status 200. |
| 4 | `deleteStudent(req, res)` | Validate the ID, find and remove that record, and respond with status 200 and `{ "message": "Student deleted successfully" }`. |

Use a monotonically increasing counter for IDs. Using array length as the next ID can create duplicates after deletion. PUT is a full replacement of the editable fields, so all four fields remain required. Every controller must finish every request by sending one response, including validation and missing-record cases.

All errors should return a JSON object with a readable `message`, for example:

```json
{ "message": "Student not found" }
```

Use 400 for invalid input and 404 for a missing student. Unexpected server errors should return 500 with a safe message. Do not return a success code for a failed operation.

### API contract to implement

| Method | URL | Request body | Success response |
| --- | --- | --- | --- |
| GET | `/api/students` | None | 200, array of student objects |
| POST | `/api/students` | Four student fields | 201, created student object |
| PUT | `/api/students/:id` | All four student fields | 200, updated student object |
| DELETE | `/api/students/:id` | None | 200, object with a success `message` |

For POST and PUT, select **Body > raw > JSON** in Postman, using this example:

```json
{
  "name": "Taylor Reyes",
  "gender": "Prefer not to say",
  "section": "BSIT 4A",
  "hobby": "Reading"
}
```

The request must include `Content-Type: application/json`. Successful POST adds a numeric `id` to that object. Use the returned ID for subsequent requests.

## Part B: React functions

Complete the seven functions inside `client/src/App.jsx`. State and event bindings are already supplied. The submit bindings already call `event.preventDefault()`. Keep the handlers in `App` so they can access its state.

| Task | Function | Required behavior |
| --- | --- | --- |
| 5 | `fetchStudents()` | Set loading, clear the previous error, GET `API_URL`, check `response.ok`, parse the response, and call `setStudents`. Show an error for a failed request. Always finish by clearing loading. It is already called on mount and by Refresh students. |
| 6 | `handleInputChangePost(event)` | Read `event.target.name` and `event.target.value`. Update that property of `newStudent`, preserving the other fields. |
| 7 | `handleAddStudent(event)` | POST `newStudent` as JSON. Check the result, show success feedback, reset the add form on success, and await `fetchStudents()` to refresh the table. |
| 8 | `handleInputChangePut(event)` | Update the matching property of `newStudentPut`, preserving the other fields, including `id`. |
| 9 | `handleUpdateStudent(event)` | PUT the four editable fields to `API_URL` followed by `/` and the entered ID. Show feedback, reset the update form on success, and refresh the table. |
| 10 | `handleDeleteChange(event)` | Update `deleteId` from the input value. |
| 11 | `handleDeleteSubmit(event)` | DELETE the URL for `deleteId`. Show feedback, clear the delete input on success, and refresh the table. |

Use the built-in browser `fetch`; no Axios is needed. POST and PUT must use JSON headers and `JSON.stringify` for the body. A 400 or 404 response does not cause `fetch` to throw automatically: check `response.ok` and display the server's `message`. Catch network failures as well.

Use the supplied `message` and `error` states for feedback. Clear stale feedback at the beginning of an action. Keep form values after a failure so users can correct them. Use `loading` to disable actions during requests, and always reset it after the action completes. Avoid reporting a successful save if the server rejected the request.

## Manual acceptance checklist

- [ ] GET initially returns the two seed students with status 200.
- [ ] Valid POST returns 201 and a new unique ID; GET includes the record.
- [ ] PUT changes the intended record, keeps its ID, and returns 200.
- [ ] DELETE removes the intended record and returns 200.
- [ ] GET returns `[]` when every student is deleted.
- [ ] Creating after deletion does not reuse an ID within the running server.
- [ ] Missing fields, whitespace-only strings, wrong types, and invalid IDs return 400 without changing data.
- [ ] Updating or deleting a valid but absent ID returns 404.
- [ ] React displays server records and refreshes after every successful mutation.
- [ ] React displays success and error feedback, loading, and the empty-table message.
- [ ] A failed submission keeps the entered values.
- [ ] Stopping the backend produces a readable frontend error after a request.
- [ ] Refreshing the browser preserves records while the backend keeps running.
- [ ] Restarting the backend resets the records to the two seed students.

## Runtime storage limit

All users connected to this one running server share its array. Stopping, restarting, or automatically reloading the server with `node --watch` discards changes. Client refreshes do not reset the server array. No data is written to a database, browser storage, or disk. Use fictional classroom data. Authentication, deployment, search, and persistence are outside this activity.
